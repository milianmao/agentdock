# AgentDock Computer Use 契约规范 v1.0.0

> 版本：1.0.0 · 状态：SDD（Phase 2，v2 修订：宿主代理路线）· 适用平台：macOS + Windows（由 Codex 桌面端提供插件决定）
> 关联：MCP 工具层（`internal/app`）↔ 工具实现（`internal/tool/computer`）↔ 宿主客户端（`internal/codexhost`）↔ `codex app-server` 子进程 ↔ Codex 内建 `computer-use` 插件
> **本版路线**：AgentDock **不自研桌面执行器**，改为借本地 Codex 作为宿主——拉起 `codex app-server`，用 `mcpServerStatus/list` 发现插件与其工具，用 `mcpServer/tool/call` 代理执行。上一版（自研 executor.sock / Swift 执行器 / 17 个 `COMPUTER_*` 码）已整体作废，理由见 §0.5。

## 0. 范围与需求边界（Phase 1 产出）

### 0.1 目标

让 AgentDock 的 MCP 客户端具备与 Codex 一致的桌面操作能力：模型先发现插件的真实工具清单（`computer_status`），再用通用代理（`computer_call`）调用官方 `computer-use` 插件的工具，得到**文本形式的无障碍树 + inline image 截图**。

三条硬边界：

1. **不重定义工具 schema**：插件通过 `mcpServerStatus/list` 广播的 `inputSchema` 是唯一事实源，AgentDock 只透传，不镜像 11 个工具、不做字段改名。
2. **不实现执行器**：macOS 上无障碍客户端必须由 OpenAI 签名的父进程启动（非签名父进程 pipe 拉起 `SkyComputerUseClient` 会被 `SIGKILL`，Code Signature Invalid）。AgentDock 只做 JSON-RPC 转发。
3. **不做模型侧授权**：授权由 Codex 宿主与 Codex 配置文件（`[computer_use.windows] always_allowed_app_ids` 等）承担；AgentDock 对宿主发来的审核类 ServerRequest 一律自动拒绝（§5.2），不暴露 approve 工具。

### 0.2 原生工具映射表（11 项，全部 1:1 透传）

官方 `computer-use` 插件的工具清单取自 `ToolDefinitions.swift`（本地逆向镜像 `packages/OpenComputerUseKit/Sources/OpenComputerUseKit/ToolDefinitions.swift:34-190`）：

### 0.3 为何不做「11 个工具一一映射」

| 方案 | 否决理由 |
|---|---|
| 每个原生工具注册一个 `computer_*` MCP 工具 | 插件 schema 随版本演进（`click_method`、`key_method`、`window_placement` 均为后加字段）。镜像即复制，复制即漂移；插件升级后 AgentDock 的 schema 立刻过期，且过期是静默的（参数被 `additionalProperties:false` 拒掉）。 |
| AgentDock 侧补默认值与枚举校验 | 默认值属插件语义（`text_limit` 默认 500、`max_tree_nodes` 默认 1200、`pages` 默认 1）；复制默认值等于把插件内部实现冻结在 AgentDock 里。 |
| 只映射高频 4 个工具 | 模型拿不到 `query`/`select_text` 就退化到像素坐标，命中率与官方差距无法解释，也无法用同一套契约测试覆盖。 |
| **通用代理（本方案）** | 一个 `arguments: OpenObject` 承接任意工具参数；schema 事实源唯一；新增原生工具零改动。代价：`computer_call` 的 `tool` 拼写错误只能在调用期发现——由 `computer_status` 输出的真实工具名列表消除。 |

### 0.5 已否决方案

| 方案 | 否决理由 |
|---|---|
| A. 自研桌面执行器（Swift AX/CGEvent 执行器 + Windows `user32`+UIA 直连） | 上一版设计。macOS 受签名约束无法落地（非 OpenAI 签名父进程拉起无障碍客户端即被系统 `SIGKILL`）；Windows 需手写 `INPUT` 联合体与 UIA COM，测试面覆盖不了真实 UI；两端各一套实现，维护成本约为本方案的 5 倍。 |
| B. 直连 `SkyComputerUseClient`／`Codex Computer Use.app` | 闭源二进制，路径与版本发现不可靠；`SIGKILL` 签名约束同上；与用户 `CODEX_HOME` 的插件状态存在写入冲突。 |
| C. 混合（Windows 自研 + macOS 借宿主） | 观察面、错误语义、坐标模型全不一致，契约无法统一，测试矩阵翻倍。 |
| D. 扩展现有 `browser_*` 工具覆盖桌面 | `browser_*` 寻址模型是 DOM selector / CDP target，桌面是无障碍树 + 截图像素坐标；混入同一工具会破坏既有 output contract。 |
| E. 让模型直接调 Codex 自己的 MCP 客户端（不经 AgentDock） | AgentDock 无调用记录、无状态面板、无法与自身权限模型统一；且 MCP 客户端通常只连一个 server，跨客户端不可组合。 |

## 1. 错误分层

三层，互不越界。

### 1.1 传输层：`CODEXHOST_*`（`internal/codexhost/errors.go:11-24`）

宿主子进程、JSON-RPC 连接与协议失败。共 12 个常量，原样落在 `details.codex_code`，供日志与面板区分「没装 Codex」与「宿主拒了这次调用」。

| 错误码 | 可重试 | 说明 |
|---|---|---|
| `CODEXHOST_CODEX_NOT_FOUND` | 否 | PATH 与配置里都找不到 `codex` 可执行文件 |
| `CODEXHOST_NOT_RUNNING` | 否 | 客户端尚未启动或已关闭时发起调用 |
| `CODEXHOST_START_FAILED` | 是 | `exec` 子进程启动失败、管道打开失败、`processcontrol.Attach` 失败 |
| `CODEXHOST_PROTOCOL_ERROR` | 否 | 请求参数无法序列化为 JSON |
| `CODEXHOST_CONNECTION_CLOSED` | 是 | 子进程退出或连接已关闭，请求未完成 |
| `CODEXHOST_CONNECTION_FAILED` | 是 | 读写失败、`id` 无对应 pending 的兜底包装 |
| `CODEXHOST_REQUEST_CANCELED` | 是 | 调用方 `context` 到期或被取消（工具层映射为 `COMPUTER_TIMEOUT`） |
| `CODEXHOST_INVALID_RESPONSE` | 否 | 宿主返回无法解码，或缺少必需字段（如 `initialize` 的 `userAgent`/`codexHome`） |
| `CODEXHOST_REMOTE_ERROR` | 否 | 宿主返回 JSON-RPC `error` 对象 |
| `CODEXHOST_INVALID_ARGUMENT` | 否 | 调用参数自身非法（如空 `threadId`、空 `server`/`tool`） |
| `CODEXHOST_MESSAGE_TOO_LARGE` | 否 | 单条 NDJSON 超过 32 MiB：出站由 `writeMessage` 预检（`:214-215`），入站由 `bufio.ErrTooLong` 映射（`:148-157`）后终止读循环 |
| `CODEXHOST_UNSUPPORTED_METHOD` | 否 | **保留码，当前不会出现在任何 AgentDock 输出里。** 宿主发起未知 ServerRequest 时，AgentDock 直接把 JSON-RPC `-32601` 回给宿主（`server_requests.go:64`），这是对宿主的应答而不是 AgentDock 侧错误；该常量只作为语义占位，供未来需要区分「我方不支持的宿主方法」时使用 |

### 1.2 工具层：`COMPUTER_*`（`internal/tool/computer/errors.go:14-19`）

AgentDock 自己的分类，**仅 4 个**，只出现在 `computer_status`/`computer_call` 输出的 `error.code` 里，用于日志与宿主面板。**不声称与官方对齐**——官方没有错误码 taxonomy。

| 错误码 | 分类 | 触发 |
|---|---|---|
| `COMPUTER_HOST_UNAVAILABLE` | runtime | 宿主不可用：`CODEXHOST_CODEX_NOT_FOUND`/`CODEXHOST_NOT_RUNNING`/`CODEXHOST_START_FAILED` |
| `COMPUTER_INVALID_ARGUMENTS` | validation | `HandleCall` 自身的防御性入参校验（`tool` 缺失、`arguments` 非对象），返回 `(nil, error)`。**注意分层**：经 `tools/call` 进入时 `Runtime.Call` 先用 `inputSchema` 校验，非法参数在更早一层以 `INVALID_ARGUMENT` 拒绝（`runtime.go:324-340`，`details.tool`/`details.reason`），`COMPUTER_INVALID_ARGUMENTS` 只在绕过 schema 层直接调 handler 时出现 |
| `COMPUTER_CALL_FAILED` | runtime | 其余传输/协议失败，含宿主报「无此 server」「无此工具」 |
| `COMPUTER_TIMEOUT` | runtime | `CODEXHOST_REQUEST_CANCELED`，即 `timeout_ms` 到期 |

刻意**不区分**「server 不存在」与「工具不存在」：宿主对两者都回 JSON-RPC error，只能靠 message 文本区分，解析文本即制造版本耦合。两者都落 `COMPUTER_CALL_FAILED`，原始 message 与 `details.codex_code=CODEXHOST_REMOTE_ERROR` 一并保留。

### 1.3 插件级失败：不映射

官方插件用「`isError: true` + content 文本」表达工具失败（样本：`appNotFound("iTerm2")`、`Computer Use is not allowed to use the app 'com.googlecode.iterm2' for safety reasons.`、`Apple event error -10000`）。AgentDock **不解析文本、不分类、不重试**，只透传，并以 `host_ok`/`is_error` 双字段区分：

| `host_ok` | `is_error` | 含义 |
|---|---|---|
| `true` | `false` | 代理成功，插件成功 |
| `true` | `true` | 代理成功，插件报错——读 `content`/`text` 文本 |
| `false` | `true` | 代理本身失败——读 `error` |

## 2. MCP 工具契约

### 2.1 注册与可用性

- 注册位置：`internal/app/specs_computer.go` 的 `computerToolSpecs()`，由 `buildToolSpecs()`（`internal/app/specs_registry.go:16`）追加。
- `Availability: requiresComputer`，实现 `func requiresComputer(cfg config.Config) bool { return cfg.CodexHostEnabled }`（`internal/app/specs.go:155-157`）。
- **注册口径是纯配置开关，不做探测**：`compileAvailableToolContracts` 在 `NewRuntime` 阶段同步执行，不得发起子进程或 IPC。Codex 是否存在、插件是否安装，全部推迟到调用期由 `computer_status` 揭示——因此 **不因平台/安装缺失而从 `tools/list` 摘除工具**。
- 注解：`computer_status` → `readOnlyToolAnnotations(false)`；`computer_call` → `mutatingToolAnnotations(true, true)`（`openWorldHint=true`，因为会改变真实桌面）。
- 不登记 `toolUIBindings`（`internal/app/mcp_apps.go:56`）。
- 配置：`AGENTDOCK_CODEX_HOST_ENABLED`（默认 `false`）、`AGENTDOCK_CODEX_EXECUTABLE_PATH`、`AGENTDOCK_CODEX_HOME`、`AGENTDOCK_COMPUTER_USE_SERVER`（默认 `computer-use`）。

### 2.2 output contract 覆盖登记

`internal/app/output_contract_coverage_test.go:51-52` 登记两条，**均不带 `IntegrationOnly`**（`:95-97` 白名单只放行 `browser_` 前缀）：

| 工具 | Variants | 依据 |
|---|---|---|
| `computer_status` | `["success"]` | 顶层无 `action`/`intent` enum |
| `computer_call` | `["success"]` | 同上；`tool` 是开放字符串，不构成 enum 选择器 |

### 2.3 `computer_status`

- **用途**：列出 Codex 宿主导出的全部 MCP server，并判定 `computer-use` 是否安装、工具清单与各自 `inputSchema`。这是**唯一**可靠的本机探测手段。
- **参数**：`server`(string, 可选过滤)、`include_tools`(bool, 默认 `true`)、`timeout_ms`(integer, 1–600000, 默认 120000)；无必填字段。
- **输出（成功）**：

```json
{
  "host_ok": true,
  "codex_home": "/home/dev/.codex",
  "servers": [
    {
      "name": "computer-use",
      "auth_status": "bearerToken",
      "runtime_status": "ready",
      "server_name": "computer-use",
      "server_version": "1.0.770",
      "tools": [
        {
          "name": "list_apps",
          "title": "List apps",
          "input_schema": { "type": "object", "properties": {}, "additionalProperties": false }
        }
      ]
    }
  ],
  "computer_use": {
    "available": true,
    "server": "computer-use",
    "runtime_status": "ready",
    "auth_status": "bearerToken",
    "tools": ["click", "drag", "get_app_state", "list_apps", "perform_secondary_action", "press_key", "query", "scroll", "select_text", "set_value", "type_text"]
  }
}
```

- **输出（宿主/插件缺失）**：

```json
{
  "host_ok": false,
  "servers": [],
  "error": {
    "code": "COMPUTER_HOST_UNAVAILABLE",
    "message": "Codex host is unavailable: Codex CLI is not installed or not on PATH",
    "category": "runtime",
    "details": { "operation": "start Codex app-server", "codex_code": "CODEXHOST_CODEX_NOT_FOUND" }
  }
}
```

- **字段语义**：`server_version` 是插件构建号（样本 `1.0.770`），对 AgentDock 不透明、不参与判定；`codex_home` 是宿主 `initialize` 实际解析出的 `CODEX_HOME`（`methods.go:51` 的 `Info()`，`service.go:159-164` 仅在非空时返回）——**`CODEX_HOME` 指错目录的表现与「插件未安装」完全一致**，这是现场误判的第一来源，故随发现结果返回；`servers[].tools` 仅在 `include_tools=true` 时出现；`computer_use.available=false` 时附带 `reason`；`computer_use` 恒存在（未命中时为 `{"available":false,"server":<配置名>,"reason":...}`）。工具名为**无序**集合，调用方不得依赖顺序。

### 2.4 `computer_call`

- **用途**：代理一次插件工具调用，原样返回 MCP content blocks。
- **参数**：`tool`(**必填**, string)、`server`(string, 默认 `computer-use`)、`arguments`(open object, 默认 `{}`)、`timeout_ms`(1–600000, 默认 120000)。
- **输出（插件成功）**：

```json
{
  "host_ok": true,
  "server": "computer-use",
  "tool": "get_app_state",
  "is_error": false,
  "content": [
    { "type": "text", "text": "App=com.apple.finder (pid 1106)\nWindow: \"docs\", App: Finder.\n    0 standard window docs\n        1 split group\n..." }
  ],
  "text": "App=com.apple.finder (pid 1106)\nWindow: \"docs\", App: Finder.\n..."
}
```

`content` 是**异构数组**：除 text 块外，当插件附带截图时还会出现 `{"type":"image","data":"<base64 PNG>","mimeType":"image/png"}` 块（`get_app_state` 在 `include_screenshot=true` 时、以及多数动作类工具返回动作后状态时）。image 块**原样透传**，其 base64 不复制进 `text`、不重编码、不落盘。

- **输出（插件工具级失败）**：

```json
{
  "host_ok": true,
  "server": "computer-use",
  "tool": "get_app_state",
  "is_error": true,
  "content": [
    { "type": "text", "text": "appNotFound(\"iTerm2\")" }
  ],
  "text": "appNotFound(\"iTerm2\")"
}
```

- **输出（代理失败）**：

```json
{
  "host_ok": false,
  "server": "computer-use",
  "tool": "list_apps",
  "is_error": true,
  "content": [],
  "text": "",
  "error": { "code": "COMPUTER_CALL_FAILED", "message": "call MCP tool: Codex rejected the request", "category": "runtime", "details": { "codex_code": "CODEXHOST_REMOTE_ERROR" } }
}
```

- **字段语义**：`content` 为插件原始 content 数组，AgentDock 不重排、不合并、不截断；`text` 是全文本块拼接的降级视图（给不能渲染 content block 的宿主）；`structured` 仅当插件返回 `structuredContent` 时出现；`error` 仅代理失败时出现。

### 2.5 content 透传与 MCP 信封

`internal/mcp/server.go:307-309` 对 `computer_call` 与 `computer_status` 都走独立分支 `computerToolEnvelope`（`:316-331`）。`computer_status` 也必须走：它的失败结果没有 `content` 块，若沿用通用信封会以 `isError=false` 报成功。

| 项 | 规则 |
|---|---|
| `content` | 取 `payload["content"]`；为空时回落单个 `text` block（`pretty(payload)`），保证客户端永远有可读内容 |
| `isError` | `payload["is_error"] == true` 或 `payload["host_ok"] != true` |
| `structuredContent` | 整个 payload 原样 |

## 3. 宿主代理契约

### 3.1 传输事实

宿主**不是 HTTP**：AgentDock `exec` 出 `codex app-server` 子进程，走 **stdio 上的换行分隔 JSON-RPC 2.0**（NDJSON）。端点标题里的 `POST /computer/status`、`POST /host/...` 是契约标识，分别等价于「MCP 工具调用」与「JSON-RPC `method`」。约束：

- 单条消息上限 `maxMessageBytes = 32 << 20`（`internal/codexhost/transport.go:17`），双向约束：出站超限不写入，入站超长使 scanner 返回 `bufio.ErrTooLong`，两者都映射为 `CODEXHOST_MESSAGE_TOO_LARGE`；入站超长属帧边界损坏，连接随即终止、不可重试。
- 请求按 `id` 路由（`:66-108`）；未匹配 `id` 的应答被丢弃。
- 握手 `initialize` 硬超时 30 s（`internal/codexhost/client.go:23`），`thread/start` 同样 30 s（`:25`）。
- 子进程环境 = `envstore.MinimalSystemEnv()` + 显式 overlay，其中 `CODEX_HOME` 必定覆盖（`client.go:92-95`）——`MinimalSystemEnv` **不含** `CODEX_HOME`，不覆盖会让宿主加载另一套插件。
- 宿主发来的 ServerRequest 全部由 `answerServerRequest` 显式应答（§5.2），不应答会卡住 Codex 的 turn。

### 3.2 端点清单

| 端点标识 | 实现入口 | 对外工具 | 超时 |
|---|---|---|---|
| `POST /computer/status` | `Service.HandleStatus`（`internal/tool/computer/service.go`） | `computer_status` | `timeout_ms`，默认 120 s，上限 600 s |
| `POST /computer/call` | `Service.HandleCall`（同上） | `computer_call` | 同上 |
| `POST /host/initialize` | `Client.Initialize`（`internal/codexhost/methods.go:21`） | 内部 | 30 s |
| `POST /host/thread/start` | `Client.StartThread`（`methods.go:71`）→ `EnsureThread`（`client.go:151`） | 内部 | 30 s |
| `POST /host/mcp-servers/list` | `Client.ListMCPServers`（`methods.go:139`） | 内部（供 `computer_status`） | 取调用方 deadline，最多 50 页 |
| `POST /host/mcp-tool/call` | `Client.CallMCPTool`（`methods.go:239`） | 内部（供 `computer_call`） | 取调用方 deadline |

#### 3.3.1 computer_status

### POST /computer/status
- **用途**：宿主发现。一次调用完成「确保宿主进程 + 确保线程 + 列出 MCP server」，并挑出 `computer-use`。
- **权限**：本机用户，可执行 Codex；无网络要求。
- **请求体**：
```json
{
  "server": "computer-use",
  "include_tools": true,
  "timeout_ms": 120000
}
```
- **成功响应**：
```json
{
  "host_ok": true,
  "codex_home": "/home/dev/.codex",
  "servers": [
    {
      "name": "computer-use",
      "auth_status": "bearerToken",
      "runtime_status": "ready",
      "server_name": "computer-use",
      "server_version": "1.0.770",
      "tools": [
        { "name": "list_apps", "input_schema": { "type": "object", "properties": {} } }
      ]
    }
  ],
  "computer_use": {
    "available": true,
    "server": "computer-use",
    "runtime_status": "ready",
    "auth_status": "bearerToken",
    "tools": ["click", "drag", "get_app_state", "list_apps", "perform_secondary_action", "press_key", "query", "scroll", "select_text", "set_value", "type_text"]
  }
}
```
- **失败响应形状**：宿主不可达时形状不变——`host_ok=false`、`servers=[]`、`computer_use` 仍存在（`available=false`、`server` 为配置值、`reason` 说明「清单未知」）、`error` 给出 `code`（`service.go:345-356`）。客户端可无条件读 `computer_use.available`，无需先判断 `host_ok`。
- **结果字段**：`codex_home` 取自宿主 `initialize` 应答的 `codexHome`（`methods.go:51`），宿主未完成握手或字段为空时**省略该键**而非返回空串；`include_tools=false` 时不返回 `tools`；`server` 只过滤 `servers[]`，**绝不**影响 `computer_use` 的判定（判定在过滤之前完成，`service.go:100-114`），因此 `server` 命中空集时 `servers=[]` 而 `computer_use.available` 仍可能为 `true`，且 `host_ok` 恒为 `true`（只要 `mcpServerStatus/list` 本身成功）。
- **错误码**：
| 错误码 | 说明 |
|---|---|
| `COMPUTER_HOST_UNAVAILABLE` | Codex 未安装、未启动或启动失败（`details.codex_code` 区分） |
| `COMPUTER_TIMEOUT` | `timeout_ms` 内未完成 |
| `COMPUTER_CALL_FAILED` | `mcpServerStatus/list` 协议失败或返回无法解码 |

#### 3.3.2 computer_call

### POST /computer/call
- **用途**：代理一次插件工具调用，content blocks 原样返回。
- **权限**：本机用户；真实桌面权限由 Codex 宿主与插件决定（TCC / Windows 前台会话）。
- **请求体**：
```json
{
  "server": "computer-use",
  "tool": "get_app_state",
  "arguments": { "app": "Finder" },
  "timeout_ms": 120000
}
```
- **成功响应**：
```json
{
  "host_ok": true,
  "server": "computer-use",
  "tool": "get_app_state",
  "is_error": false,
  "content": [
    { "type": "text", "text": "App=com.apple.finder (pid 1106)\nWindow: \"docs\", App: Finder.\n    0 standard window docs" }
  ],
  "text": "App=com.apple.finder (pid 1106)\nWindow: \"docs\", App: Finder.\n    0 standard window docs"
}
```
- **参数校验（两层，按发生顺序）**：
  1. **schema 层**（`tools/call` 必经）：`tool` 为必填字符串、`arguments` 声明为开放对象，非法值由 `Runtime.Call` 以工具错误 `INVALID_ARGUMENT` + `details.reason` 拒绝，MCP 信封 `isError=true`（`runtime.go:324-340`）。
  2. **handler 层**（防御性，绕过 schema 时才可见）：`HandleCall` 对缺失 `tool`、非对象 `arguments` 返回 `COMPUTER_INVALID_ARGUMENTS`，**不**降级成 `{}` 转给插件——降级只会换来一条误导性的插件 schema 报错（`service.go:203-213`）。
- **结果字段**：`content` 允许追加 `{"type":"image","data":"<base64>","mimeType":"image/png"}` 块（见 §2.4）；`arguments` 缺省为 `{}`；`server` 缺省为 `AGENTDOCK_COMPUTER_USE_SERVER`；`structured` 只在插件返回时出现；`text` 只拼接 `type=="text"` 的块。
- **错误码**：
| 错误码 | 说明 |
|---|---|
| `COMPUTER_INVALID_ARGUMENTS` | `tool` 为空，或 `arguments` 不是 JSON 对象（handler 层防御校验）。经 `tools/call` 时同类非法参数会先被 schema 层以 `INVALID_ARGUMENT` 拒绝，两者都不产生 `host_ok=false` |
| `COMPUTER_HOST_UNAVAILABLE` | 宿主不可用 |
| `COMPUTER_TIMEOUT` | `timeout_ms` 到期 |
| `COMPUTER_CALL_FAILED` | 其他传输/协议失败，含宿主不认识该 server 或该工具 |

## 5. 通信协议契约

### 5.1 传输矩阵

| 链路 | 形态 | 消息上限 | 超时 |
|---|---|---|---|
| MCP 客户端 ↔ AgentDock | 既有 HTTP/stdio，不变 | 既有 | 既有 |
| AgentDock ↔ `codex app-server` | stdio NDJSON JSON-RPC 2.0 | 32 MiB | 每次调用由 `timeout_ms` 决定；握手/建线程 30 s |
| 宿主 ↔ 插件 | Codex 内部（进程内/其自管 IPC） | 不归 AgentDock 管 | 不归 AgentDock 管 |

### 5.2 宿主 ServerRequest 应答（10 个方法全覆盖）

宿主会把「需要人工审核」的请求发给客户端。AgentDock 是无人值守代理，必须**显式**拒绝——沉默会让 Codex 的 turn 挂起。应答形状严格按 Codex 生成的 schema（`internal/codexhost/testdata/schema/`，已过 `jsonschema-go` 校验）：

| method | 应答 | 语义 |
|---|---|---|
| `item/commandExecution/requestApproval` | `{"decision":"decline"}` | 拒绝执行命令 |
| `item/fileChange/requestApproval` | `{"decision":"decline"}` | 拒绝改文件 |
| `item/tool/requestUserInput` | `{"answers":{}}` | 无人工输入 |
| `mcpServer/elicitation/request` | `{"action":"decline"}` | 拒绝 MCP elicitation |
| `item/permissions/requestApproval` | `{"permissions":{"fileSystem":null,"network":null},"scope":"turn"}` | 不扩权 |
| `item/tool/call` | `{"contentItems":[],"success":false}` | 未注册动态工具 |
| `applyPatchApproval` / `execCommandApproval` | `{"decision":{"denied":{"rejection":"agentdock: automatic denial ..."}}}` | 旧版对象形态的拒绝 |
| `account/chatgptAuthTokens/refresh` / `attestation/generate` | JSON-RPC error `-32050` | AgentDock 不持有 ChatGPT 凭据 |

未知方法 → 直接回 JSON-RPC `-32601`（`server_requests.go:63-65`）；这是对宿主的应答，不产生 AgentDock 侧错误码（`codexhost.CodeUnsupportedMethod` 为保留常量，见 §1.1）。任何应答 handler panic 被 `recover()` 转为 `-32603`（`transport.go:165-186`），不拖垮读循环。

### 5.3 生命周期

| 阶段 | 行为 |
|---|---|
| 构造 | `NewRuntime` 只 `toolcomputer.New(...)`，不启动子进程（`internal/app/runtime.go:163-168`） |
| 首次调用 | `Service.acquire` → `connect` 持锁 → `codexhost.Start`（发现可执行文件、合并环境、起子进程、`processcontrol.Attach`、握手）→ `EnsureThread` |
| 后续调用 | 复用 client 与 thread，只加锁取引用 |
| 失败 | 启动或建线程失败即 `client.Close()` 回收子进程，不缓存半成品 |
| 关闭 | `Runtime.Close()` 在 `r.command.Close()` **之前**调 `r.computer.Close()`（`runtime.go:244-252`）；`Close` 幂等，从未启动时直接返回 |
| 子进程退出 | transport 关闭所有 pending，进行中的调用返回 `CODEXHOST_CONNECTION_CLOSED`（可重试）；`Service` 收到终态错误时立刻丢弃缓存 client（`service.go:231-248`），**下一次调用自动重起子进程**，并重建 thread |

### 5.4 并发与限流

- 同一 `Service` 内所有调用串行建立连接（`s.mu` 覆盖 `connect` 全程），建立后并发调用只共享 transport。
- 连接终态错误（`CODEXHOST_CONNECTION_CLOSED`/`CODEXHOST_CONNECTION_FAILED`/`CODEXHOST_NOT_RUNNING`）触发缓存 client 丢弃（`service.go:231-248`，`isTerminalHostError` `:218-225`）；请求超时与插件级失败**不**丢弃，避免抖动时反复重启子进程。
- transport 以 `id` 路由应答，允许并发 in-flight；写侧由 `writeMu` 串行（`transport.go:40`）。
- 无内置重试：`timeout_ms` 到期即 `COMPUTER_TIMEOUT`，重试策略归模型侧。

## 6. 降级与兜底

### 6.1 错误传播链

```text
插件工具失败 → content 文本 + isError:true
   → codexhost.ToolCallResult{IsError:true}          （原样，不转 error）
   → tool/computer: host_ok=true, is_error=true      （不设 error 字段）
   → mcp: toolEnvelope isError=true, content 原样

传输/协议失败 → codexhost.Error{Code}
   → tool/computer: hostError() 映射 4 个 COMPUTER_*，保留 details.codex_code
   → tool/computer: 返回 (result, nil)，不抛 ToolError（除 tool 缺失等参数错误）
   → mcp: toolEnvelope isError=true, structuredContent 带 error
```

### 6.2 三级降级

| 级别 | 触发 | 表现 |
|---|---|---|
| **L1 能力未启用** | `AGENTDOCK_CODEX_HOST_ENABLED=false`（默认） | 两个工具不进 `tools/list`；`Runtime.Call` 返回 `UNKNOWN_TOOL`；零运行期开销，不起子进程 |
| **L2 宿主不可用** | Codex 未安装 / 不可执行 / app-server 启动失败 / 握手失败 | `computer_status` → `host_ok=false` + `COMPUTER_HOST_UNAVAILABLE`；`details.codex_code` 指明具体原因；**不重试、不降级到别的执行路径**，AgentDock 其余功能不受影响 |
| **L3 插件不可用或工具报错** | 宿主无 `computer-use` server / 插件未授权 / 工具级失败 | 发现阶段：`computer_use.available=false` + `reason`；执行阶段：`host_ok=true,is_error=true` + 插件原文（如 `appNotFound(...)`、`... for safety reasons.`），由模型读取文本自行调整 |

### 6.3 安全边界与官方 denylist

| 约束 | 来源 | AgentDock 的处理 |
|---|---|---|
| 终端类 App 与 ChatGPT 自身禁止被操作 | 官方插件内建拒绝（样本返回 `Computer Use is not allowed to use the app '<bundle id>' for safety reasons.`） | 不绕过、不拦截、不二次判断，原样透传给模型 |
| macOS 锁屏 / 锁屏后自动化（locked use） | 官方无支持路径，需认证事务与 TCC 特批 | **不做**。AgentDock 无执行器，无解锁能力；写入风险清单 |
| Windows 必须前台会话 | 官方文档：Windows 版 Computer Use 仅在用户前台会话生效 | 不做会话探测（AgentDock 无执行器）；由插件返回失败文本 |
| 地区限制（EEA/UK/CH 不可用） | 官方文档 | 由 Codex 侧返回失败；AgentDock 只透传 |
| 授权决策 | Codex 宿主 + Codex 配置文件（如 `[computer_use.windows] always_allowed_app_ids`） | AgentDock **不提供** approve 工具、不写授权文件、不弹审核；宿主审核请求一律自动拒绝（§5.2） |
| 凭据 | 宿主自有 ChatGPT 认证 | AgentDock 不持有、不代理、不应答 `-32050` 类请求 |
