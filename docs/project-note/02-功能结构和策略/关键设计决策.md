# 关键设计决策

格式：**背景 → 备选 → 取舍 → 结果**。结果里写「现在代码长什么样」，也写「代价是什么」。

## D1. 单进程同时做 MCP Server 与设备执行器

**背景**：MCP 协议要求一个能长期驻留的服务端；设备执行（文件、命令、浏览器）天然在同一台机器上。

**备选**
- A：MCP Server 与执行器分离，用 IPC 通信。
- B：单进程，工具直接调本地 API。
- C：每个工具一个独立 MCP server 进程。

**取舍**：A 多一层序列化与生命周期协调，且工具需要跨进程传大对象（截图、文件切片）。C 会让 `agentdock_context` 变成分布式发现，且模型要管理 N 个连接。B 的代价是工具 panic 会带走整个服务 —— 已用 `observability` + 分层 recover 缓解，但 stdio 路径仍是硬伤。

**结果**：`cmd/agentdock/server.go:28 runServer` 一个进程内组装 `Runtime` + `mcp.Server` + `httpx.Serve` + 可选 `nexusbridge.Client` + 可选 `desktopcontrol.Serve`。Windows 例外：托盘与控制面板是独立进程，靠命名管道 IPC。

## D2. ToolSpec 集中注册，而非 SDK 泛型注册

**背景**：go-sdk 提供 `mcp.AddTool[T]` 泛型注册，能自动从 Go struct 生成 schema。

**备选**
- A：用泛型 `AddTool`，schema 从 struct tag 推导。
- B：手写 JSON Schema，用低层 `AddTool`。
- C：混合。

**取舍**：A 省事但三个问题无解 —— (1) struct tag 无法表达 `additionalProperties:false` 的严格性与 `oneOf` 的互斥动作；(2) 无法给不同 config 生成不同 schema（`task_manage` 的 Nexus 字段要按配置裁剪）；(3) 无法接入共享 `agentdock-protocol` 的 canonical schema。B 的代价是每个工具手写约 30 行 schema，且要人工保持与 handler 一致 —— 用启动期编译校验兜底。

**结果**：`internal/mcp/server.go:139-143` 注释明写「使用低层 AddTool，参数校验、错误码、结构化输出、UI 绑定全归 Runtime」。schema 分散在 `internal/tool/<cap>/contract.go`，provider 在 `internal/app/specs_contract.go`，组装在 `specs_<cap>.go`。

## D3. 统一 JSON Schema 输入校验，输出不校验

**背景**：commit `0c6f6de refactor(contract): 统一 JSON Schema 校验并保持兼容边界 (#248)` 之前，各工具自行校验参数，错误码与文案不一致。

**备选**
- A：每个工具自己 if/else 校验。
- B：统一在 `Runtime.Call` 编译并执行 JSON Schema validator。
- C：B + 输出也校验。

**取舍**：A 的漂移不可避免。C 会让"输出加字段"这类兼容变更变成破坏性变更 —— 对 MCP 客户端是灾难。

**结果**：`internal/app/specs_validation.go:16 compileBuiltInInputValidator` 以 schema JSON 内容为缓存键编译 validator，`Runtime.Call` 是唯一执行点。`OutputObject` 的 `additionalProperties` 固定为 `true`（`internal/tool/contract/schema.go:19`）。错误统一 `INVALID_ARGUMENT` + `tools/contract.CompactValidationError` 的可读摘要。

**代价**：输出 schema 与实现不一致只能靠测试发现（`output_contract_runtime_test.go`）。

## D4. 状态全部落文件系统，不引入数据库

**背景**：需要持久化任务、Skill、Plugin、OAuth 状态、MCP 注册表、设置。

**备选**：SQLite / BoltDB / 文件 + 原子写 + 文件锁。

**取舍**：嵌入式 DB 带来 CGO 或纯 Go 二选一（`modernc.org/sqlite` 体积大）、迁移工具、以及"用户想手工改一个值"的门槛。AgentDock 的状态量级是「几十个任务 + 十几个 Plugin」，JSON 完全够用，且用户能直接 `cat`。

**结果**：全部走 `internal/fs/atomicfile.Write`（临时文件 → chmod → Sync → rename → 父目录 fsync），并发用 `fs/processlock`（跨进程）与 `fs/filelock`（PID 所有者 + 10 分钟 stale）。目录权限统一 0700 / 文件 0600，Windows 用保护性 DACL。

**代价**：每个 store 自己实现 List/Get/Save 与尺寸上限（2 MiB / 8 MiB / 1 MiB 各不同），没有事务跨多文件。

## D5. Skill 与 Plugin 是两条独立安装链

**背景**：Skill 是「给模型读的说明文档」，Plugin 是「可含多个 Skill + 多个 MCP 组件的包」。二者形态、审核要求、更新语义都不同。

**备选**
- A：统一抽象成"包"，一套事务。
- B：两条链，共享 fs 原语。

**取舍**：A 会强制 Skill 承担版本目录、租约、MCP reconcile 的复杂度，而 Skill 只有「一个目录、一个内容摘要」。B 的代价是两套 journal 格式。

**结果**
- Skill：单目录 swap。`prepared` → `candidate_published` 两阶段，同 digest 直接 no-op（`Changed:false`），无版本概念。
- Plugin：多版本目录 + `ActivationTransaction` + 三级租约 + MCP runtime reconcile。提交点唯一：`FinalizeActivation` 内的 `store.Save(Candidate)`。

二者共享的安全原语：`os.OpenRoot`、`atomicfile`、`filelock`、ZIP 限额（解压 256 MiB / 10000 文件）。

## D6. 动态 MCP 用代理工具，不展开到 tools/list

**背景**：用户可注册任意远端 MCP server，每个可能有几十个工具。

**备选**
- A：把远端工具全部合并进 `tools/list`。
- B：4 个固定代理工具（search / inspect / call + manage）。

**取舍**：A 会让工具列表爆炸（100+ 条），污染模型上下文，且远端工具变更需要热更新 `tools/list`。B 的代价是模型必须多走一步 `search` → `inspect` → `call`。

**结果**：`mcp_manage` / `mcp_tool_search` / `mcp_tool_inspect` / `mcp_tool_call` 四个工具固定注册。`mcp_tool_call` 做双层校验：外层只要求 `{name, arguments}`，内层用远端 `inputSchema` 重新编译 validator。观测上冷调用 2 个 stage（`MCPRefresh` + `MCPRemoteCall`），热调用 1 个。

## D7. MCP Apps 三态开关，工具不随 UI 关闭

**背景**：MCP Apps 让工具结果能渲染成卡片，但不同宿主支持度差异大。

**备选**
- A：只做全开/全关。
- B：`full` / `compact` / `off` 三态。

**取舍**：`compact` 解决"卡片太占地方但仍想看图/看 diff"的需求。关键决定是 **UI 关闭不影响工具本身** —— 否则一个纯展示层的开关会改变协议能力。

**结果**：`internal/app/mcp_apps.go:44 toolUIBindings` 11 条绑定，每条可带 `Compact` 变体。`off` 时不注册资源、不加 `ui` 元数据，`tools/list` 与调用行为完全不变。资源数随环境变化：默认 7 个，配 Nexus +2，启 ACP +2。

## D8. Windows 用 generation + 事务，Linux 用覆盖式

**背景**：自更新最怕"更新到一半进程被杀，机器上只剩半个二进制"。

**备选**
- A：全平台 generation 目录 + 仲裁器。
- B：全平台覆盖式 + 备份。
- C：Windows 事务化，Linux/macOS 按平台能力分级。

**取舍**：`updateengine.NewTransaction` 只接受 `windows` 与 `darwin`（`internal/updateengine/contract.go:128-130`）。Windows 进程无法自我替换（文件被占用），必须靠 shim + 重启，因此事务化是刚需。Linux 可以 `rename` 覆盖运行中的二进制（inode 语义），同步流程 + 备份已足够。macOS App Bundle 整体替换，走 Arbiter。

**结果**
- Windows：`bin/` shim → `versions/v<semver>/` generation；`update/transaction.json` journal；Arbiter 独立进程做 trial/commit/rollback；`.staging-<txid>` → `MoveFileEx(WRITE_THROUGH)`。
- macOS：`AgentDock.app` 整体换，`RENAME_SWAP`，`Driver.Commit` 是空实现（旧 App 就是 rollback slot），清理在 terminal result 之后。
- Linux：备份 → `os.Rename` → `--version` → `systemctl restart` → 30s 健康轮询。**没有** `active-version.json`、没有 generation。

**代价**：三条路径三套失败语义，测试矩阵大。

## D9. 回滚用独立预算（`context.WithoutCancel`）

**背景**：trial 超时会取消传入的 ctx。如果 rollback 沿用这个 ctx，回滚一开始就失败，结果被记成 `failed` —— 而实际上文件可能已经回滚了一半。

**备选**：复用 ctx / 新开 background / `WithoutCancel` + 独立超时。

**取舍**：`WithoutCancel` 保留 trace 上下文与值，只剥离取消信号，是最精确的语义。

**结果**：`internal/updateengine/arbiter.go:105 rollback` 先写 `PhaseRollback` journal，再用 `context.WithTimeout(context.WithoutCancel(ctx), 3*time.Minute)`。注释原文解释了原因。这条纪律同样适用于 Plugin 移除链。

## D10. cloudflared 解耦为可选 managed component

**背景**：Cloudflare Tunnel 从"基础安装强依赖"变成"高级自托管能力"。把 cloudflared 打进主安装包会让包体膨胀、升级耦合、且安全审计面变大。

**备选**
- A：继续随包分发。
- B：运行时下载，无版本管理。
- C：独立组件子系统（版本目录 + catalog + 激活指针 + 信任校验）。

**取舍**：B 无法回滚、无法钉版本、无法做供应链校验。C 的代价是多一套 catalog 与 CLI。

**结果**：`internal/component` 提供 `Store{Status,Resolve,ImportLegacy,Install,Update,Uninstall}`；`components/cloudflared/versions/<v>/` + `active.json`；内嵌 `catalog-v1.json`（schema v2 / revision 3）作 baseline；解析顺序 `--catalog-url` → 远程 → 本地缓存 → 内嵌；下载先 R2 mirror 后官方，两边用同一 pinned SHA-256。信任：Windows Authenticode、macOS `codesign --verify --strict`、Linux 拒绝 legacy 导入。

## D11. 机器分发走 R2，GitHub Release 只做人工下载

**背景**：GitHub Release 的下载统计与 CDN 行为不可控；自更新需要稳定、可保留策略的机器端点。

**备选**：全走 GitHub / 全走自建 / 双轨职责分离。

**取舍**：双轨需要保证「同一份已通过 gate 的 candidate 字节」出现在两个渠道，不能重复构建。这条约束比单一渠道严格，但换来了 GitHub 页面干净（只放用户真正要下载的 5 类资产）。

**结果**：`https://download.nexusdock.co` 承载 `latest.json`、版本化 Release 快照、`components/v1/catalog.json`。GitHub Release 只展示 Windows Setup、macOS DMG、Linux amd64/arm64 归档、`SHA256SUMS.txt`。R2 保留策略只留当前 + 上一 Stable，`components/cloudflared/<version>/` 不可变。

## D12. 自演化只在 AgentDock，NexusDock 只存 Recall/Workflow

**背景**：早期方案设想把 Evolution 放到 NexusDock 侧，做跨设备学习。

**备选**
- A：Evolution 在 NexusDock，设备上报会话。
- B：Evolution 在 AgentDock，NexusDock 只做存储。

**取舍**：A 需要 Conversation ingest、全量会话 DB、Evolution leader 选举、成熟度策略 —— `docs/self-evolution-architecture.md:614` 明确把这一整串列为**不建设**。B 让演进数据留在设备本地，NexusDock 只承担跨设备同步的 Recall 与 Workflow 模板。

**结果**：`evolve` 工具只在设备侧；`intent` 四态 `propose`/`bind`/`supersede`/`retract`；Stage 3 外部模型**没有裁决权**。防自证硬规则：`final_review` 由 `record` 之外的结构化证据驱动，`review_revision` 单调递增。

## D13. 桌面端原生重写（AppKit / WinUI 3）

**背景**：`docs/desktop-native-ui-rebuild.md` 记录，PR #181 的多轮样式调整无法达到目标质感。诊断结论是：WPF 需要维护大量自定义样式才能接近 Fluent，AppKit 纯手写布局成本高。

**备选**：继续 WPF/AppKit 精修 / Electron / 平台原生重写。

**取舍**：Electron 会引入一个 Chromium + Node 的运行时（体积 ~150 MB），且与"控制面板"的轻量定位矛盾。原生重写的一次性成本高，但之后的页面维护成本低。

**结果**：macOS 34 个 Swift 文件（AppKit + 少量 SwiftUI）；Windows WinUI 3 self-contained（~145 MB），5 个页面 + 托盘。目标不是像素一致，而是"第一眼同一个 AgentDock，第二眼是平台原生应用"。桌面端不持有业务状态，只读 Runtime API 与 `DispatchControlRequest`。

## D14. 图片走标准 MCP Apps 优先，ChatGPT 专有能力作 fallback

**背景**：`view_image` 返回标准 MCP image content，但"让下一轮模型看到图片"在不同宿主能力不同。

**备选**：只用标准能力 / 只用 ChatGPT `uploadFile` / 标准优先 + fallback。

**取舍**：只用标准会让 ChatGPT 用户体验退化；只用专有会锁死宿主。

**结果**：`docs/image-model-context.md` 记录：优先 `ui/update-model-context` + `ui/message`；宿主未暴露标准能力时才回退 `uploadFile` / `widgetState.imageIds`。关闭 MCP Apps 或调用失败时，`view_image` 的基础图片返回能力不变。

## D15. 静态 Token 与 OAuth 并存

**背景**：自托管用户想要一个口令就开跑；ChatGPT 等远端 MCP 客户端则要求 OAuth 2.1 + PKCE。

**备选**：只做静态 Token / 只做 OAuth / 并存。

**取舍**：只做静态 Token 无法接 ChatGPT；只做 OAuth 让自托管部署必须先配 3 个环境变量才能用。并存的双通道判定只有 3 行（`mcp_endpoint.go:45-58`），代价可接受。

**结果**：`AuthRequired() = AuthToken != "" || OAuthEnabled`。`/mcp` 与 `/context` 先算 `staticOK || oauthOK`。非回环绑定且两者都空时 `ValidateAuth` 直接拒绝启动。

**已知缺口**：`AGENTDOCK_AUTH_TOKEN` 无强度校验；Bearer 失败无限流（可在线穷举）。→ 详见 [已知问题与陷阱](../06-迭代与变更/已知问题与陷阱.md)

## D16. 上下文工具拆成 `agentdock_context` + `workspace_context`

**背景**：设备能力总览（每天变）与项目规则（每次请求变）生命周期完全不同。

**备选**：一个工具返回全部 / 拆分。

**取舍**：合并会让 `AGENTS.md` 的 128 KiB 预算挤占能力索引，且缓存无法分层。`docs/agents-context.md` 明确：`agentdock_context` 只返回 Runtime/Skill/MCP/Workflow/Recall/ACP + 稳定操作规则；项目规则由 `workspace_context` 按请求读。

**结果**：两个工具。规则文件只认两类 `AGENTS.md`：全局固定 `~/.agentdock/AGENTS.md`，工作区从 workspace root 逐级继承到 `workdir`。预算 64 KiB/文件、128 KiB/总量、最多 64 个目录。
