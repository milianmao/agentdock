# 设计模式与策略

本文只记录**贯穿全仓库的实现约定**。具体业务链路的顺序 → 详见 [业务流](../03-核心数据业务流/README.md)。

## 1. 注册表模式：ToolSpec 单点注册

问题：31 个工具如果散落在 switch 里，新增一个要改 5 处，且顺序不稳定。

策略：`internal/app/specs_registry.go:5 buildToolSpecs` 按 14 组能力**显式顺序**拼接，每组在自己文件里返回 `[]ToolSpec`。包初始化时 `indexToolSpecs`（`:29`）建索引，并 panic 于四类缺陷：

| 缺陷 | 后果 | 为什么 panic 而非 error |
|---|---|---|
| 空 `Name` | 索引键为空 | 永远是编码错误，不可能由配置触发 |
| `nil Contract` | `tools/list` 缺 schema | 同上 |
| `nil Handler` | 调用必然失败 | 同上 |
| 重名 | 后者静默覆盖前者 | 静默覆盖是**最难排查**的故障 |

启动期还有第二道闸：`compileAvailableToolContracts`（`internal/app/specs.go:128`）对每个可用 spec 编译 input validator，失败返回 error 让进程退出。

**只有 input 侧做运行时校验**。`output schema` 用于 `tools/list` 描述与测试断言，运行期不校验 —— 这是刻意的：输出加字段不应导致老客户端报错（`OutputObject` 在 `internal/tool/contract/schema.go:19` 把 `additionalProperties` 设为 `true`，正是同一取向）。

## 2. 契约所有权分离

三层分工，禁止越界：

| 层 | 位置 | 职责 |
|---|---|---|
| Schema 定义 | `internal/tool/<cap>/contract.go` | 纯数据，`InputObject`/`BoundedInteger`/`OpenObject` 组合 |
| Contract provider | `internal/app/specs_contract.go` | `staticToolContract` 包一层，或 `canonicalToolContract` 走共享 `mcpcontract` |
| Spec 组装 | `internal/app/specs_<cap>.go` | 绑定 Name/Title/Description/Annotations/Availability/Handler |

`ToolSpec.definition(cfg)`（`specs.go:78`）统一组装：用 `mcpcontract.AnnotationContract` 覆盖手写 annotations，并挂上 `toolUIBinding(name)`。这样**注解与 UI 绑定只有一处真源**。

`InputObject` 默认 `additionalProperties: false`（`schema.go:5` 注释明示「结构已知的工具默认拒绝未知字段」）；真正动态的字段（如 `mcp_tool_call.arguments`）必须在该 property 上显式声明 `additionalProperties: true`。这条规则把"模型幻觉参数"在协议层就打掉。

## 3. 显式依赖注入 + 组合根

`Runtime`（`internal/app/runtime.go:39`）是所有 Service 的唯一持有者。工具包之间不互相 import（验证：`grep -rln 'internal/app"' internal/tool/` 为空）。跨模块能力通过**函数值**注入而非接口包：

| 注入点 | 类型 | 用途 |
|---|---|---|
| `toolfile.SkillResourceResolver` | `func(ctx, raw) (abs, display string, release func(), err error)` | 文件工具解析 `skill://` URI，同时拿到租约释放函数 |
| `toolfile.CommandEnv` | `func(skillName string, extra map[string]string) ([]string, error)` | 让文件工具也知道命令环境（模板渲染） |
| `toolcommand.SkillLease` | 同构 | 命令工具在子进程生命周期内持有 Skill 租约 |
| `toolcommand.SkillResolver` | `func(ctx, ref) (...) ` | 解析 `skill_ref` 到物理路径 |

好处：`tool/file` 不需要知道 `skill.Manager` 存在，测试可以传闭包。代价是构造顺序必须严格 —— 由 `NewRuntime` 的线性代码保证，失败按逆序 Close。

## 4. 安全边界：三层路径校验

`filepath.Clean` 被明确声明**不是安全边界**（`internal/workspace/workspace.go:190` 注释）。真正边界是：

```
1. os.OpenRoot / os.OpenInRoot   → 内核级目录锚定，符号链接不能逃逸
2. filepath.IsLocal              → 拒绝绝对路径/上跳/Windows 设备名
3. filepath.Rel 前缀校验          → 相对路径结果不得以 ".." 开头
```

使用分布：

| 机制 | 主要使用点 |
|---|---|
| `os.OpenRoot` | `publicartifacts/http.go`、`agentinstructions/instructions.go:173`、`plugin/store.go` |
| `filepath.IsLocal` | `publicartifacts/cleanup.go:55`、`config/paths.go` |
| `filepath.Rel` 前缀 | `config/paths.go:35-37/55-57/73-75/92-94`、`envstore/validation.go:20`（用 `filepath.Base(name) != name` 拒绝分隔符） |

附加防线：`Lstat` + regular/non-symlink 判定、`O_NOFOLLOW|O_NONBLOCK`（`agentinstructions/open_unix.go:7`）、`EvalSymlinks` 后重新求实路径（`workspace.ResolveExisting/ResolveForWrite`）。

**已知 TOCTOU 窗口**：`ResolveForWrite` 在 `EvalSymlinks` 与实际写入之间可被本机攻击者竞态替换父目录。这是记录在案的约束，不是遗漏。

## 5. 事务模式：stage → trial → commit → rollback

四种事务实现，共享同一套骨架但**日志与回滚单位不同**：

| 事务 | 日志载体 | 回滚单位 | 幂等键 |
|---|---|---|---|
| Skill 安装 | `SwapTransaction` journal（`skill/state/transaction.go:18`） | 单个目录 swap | `content_digest` |
| Plugin 安装/更新 | `ActivationTransaction`（`store.SaveActivationTransaction`） | 版本目录 + MCP runtime | `review-v1:sha256:` + digest |
| 自更新 | `updateengine.Transaction`（`<root>/update/journal.json`） | 二进制 generation | `ActiveVersion` |
| CLI 安装 | `rollbackJournal`（`installer/journal.go:46`） | 文件快照 + 服务状态 | `transactionID` |

共同不变量：

1. **先写日志再动文件**（journal-first）。进程被杀后靠日志恢复，不靠内存状态。
2. **恢复在启动时执行**：`plugin.recoverInterruptedActivations`、`skill.recoverSwapLocked`、`updateengine.Arbiter.Run` 按 `State` 分派。
3. **回滚用独立预算**：`updateengine.arbiter.go:105 rollback` 使用 `context.WithoutCancel` + `rollbackRecoveryTimeout=3min`。否则 trial 超时会把"已物理回滚"记成 `failed`。
4. **提交点唯一且显式**：Plugin 是 `FinalizeActivation` 里的 `store.Save(Candidate)` —— 之前所有步骤都还在 candidate 目录。
5. **阶段字符串是持久化契约**：`skill` 的 `prepared`/`candidate_published`（`transaction.go:110`）改了就要写迁移。

## 6. Feature gate：三态可用性

`Availability func(config.Config) bool`（`internal/app/specs.go`），只有三个实现：

```go
requiresNexus   = cfg.NexusEndpoint != ""
requiresBrowser = cfg.BrowserEnabled
requiresACP     = cfg.ACPEnabled
```

影响面**必须同步**：`tools/list`、`agentdock_context` 能力索引、`toolValidators` 编译、MCP Apps 资源集合。少同步一处就会出现"工具不可见但可调用"或反之。

示例：`NexusEndpoint != ""` 同时控制 `evolve`、4 个 `recall_*`、`workflow_template_manage`，以及额外 2 个 UI 资源（Recall/Workflow）；`ACPEnabled` 控制 3 个 `acp_*` 工具与 2 个 UI 资源（ACPStatus/ACPPrompt）。

## 7. 归一化适配器：多来源 → 单一规范

三个地方用同一思路（发现差异 → 规范化 → 只对规范形态做业务）：

### Plugin 三格式

`internal/plugin/format.go:18-20` 定义 `portable` / `openai` / `claude`。`normalizeStagedPlugin`（`:30`）先 `detectPluginFormat`，portable 直接校验，另两种转成 canonical 后**再快照一次**，之后所有逻辑只见 portable 结构。转换失败统一 `PLUGIN_FORMAT_CONVERSION_FAILED` 并带阶段后缀（`format.digest`/`format.snapshot`/`format.canonical_snapshot`）。

### Skill 两种来源

| 来源 | 数据目录 | env scope |
|---|---|---|
| `managed` | `config.SkillDataDir` | `ScopeSkill` |
| `plugin` | `config.PluginSkillDataDir` | `ScopePluginSkill` + `EnsureDataDir` + `PLUGIN_DATA_DIR` |

上层 `skill_ref` 是 `skill://managed/<name>` 或 `skill://plugin/<plugin>/<name>`，模型不需要知道物理位置。

### ACP 多 profile

`ACP_PROFILES` 每项一个 `acpruntime.Manager`，`toolacp.Multi` 按 `agent` 字段分发。对模型暴露的是统一的 `acp_session`/`acp_prompt`/`acp_interaction`，profile 差异（Claude/Codex/Grok 的协议细节、steering 支持度）在 adapter 内部消化。

## 8. 双传输共享核心

`Server` 与 `Runtime` 是同一份，stdio 与 HTTP 只在入口分叉：

| 关注点 | stdio | HTTP |
|---|---|---|
| 认证 | 无（进程权限即边界） | Bearer + OAuth 双通道 |
| 请求体限制 | 无 | 1 MiB + 单 JSON 值 |
| 取消传播 | `context.Background()`，信号即退 | `PropagateRequestCancellation: true` |
| panic 后果 | 进程崩溃 | net/http 关连接 |

设计意图：**业务代码不需要感知传输**。代价是 stdio 上的 panic 无人拦截 —— 见 [已知问题与陷阱](../06-迭代与变更/已知问题与陷阱.md)。

## 9. 观测旁路

`observability.Recorder` 在 `Runtime.Call` 的 `defer observeToolCall` 中写入，**字段白名单**：tool / source / duration / ok / error_code / error_category / trace_id / span_id / stages。参数与结果正文永不入库。

`Recorder` 环形缓冲容量 500（`recorder.go:11`），`MaxStagesPerExecution = 16`（`stage.go:13`）。stage 是诊断动态 MCP 冷/热路径的关键：冷调用 2 个 stage（refresh + remote call），热调用 1 个。

`Source` 枚举区分入口：`SourceMCP`、`SourceNexus`。同一个工具从不同入口调用，观测上可分离。

## 10. 并发控制：三种锁，三种语义

| 锁 | 实现 | 语义 | 使用场景 |
|---|---|---|---|
| 进程间互斥 | `fs/processlock`（系统 flock/LockFileEx） | 进程退出自动释放 | 更新 arbiter、安装器 |
| 目录锁 | `fs/filelock`（PID 所有者文件 + 心跳） | `staleAfter=10m`，活进程永不抢占 | Skill 写、任务状态 |
| 三级文件租约 | `plugin.Store.AcquireBinding/AcquireWrite/AcquireVersionRead` | 绑定窗口 / 写独占 / 版本只读 | Plugin 版本并发 |

租约分级的原因：Plugin 解析 `state → version` 只需极短窗口（`AcquireBinding`），之后长任务必须降级为 `AcquireVersionRead` 才能让写入者推进。注释（`store.go:455-456`）直接写了这条纪律。

**fail-closed 原则**：`filelock` 遇到未知所有者文件形状直接失败而不是抢占；限流器 4096 键满且无法淘汰时拒绝新请求而非放行。

## 11. 原子持久化

`fs/atomicfile.Write`（`write.go:12`）：同目录临时文件 → chmod → Windows DACL → 写 → `Sync` → `rename` → **父目录 fsync**。

父目录 fsync 容易被漏掉：没有它，rename 本身可能在崩溃后丢失。`replace_windows.go` 用 `MoveFileEx` 语义替代 rename。

所有 `*.json` 状态文件（`tasks/`、`plugins/state/`、`nexus/device.json`、`oauth/state-v1.json`、`servers.json`）都走这条路径。
