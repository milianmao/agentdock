# 已知问题与陷阱

25 条，按"现象 → 原因 → 规避"组织。全部来自代码中的实测行为或显式注释，非推测。

## A. 认证与安全（6 条）

### A1 `Bearer.Authorized` 在空 Token 时返回 `true`

**现象**：只调 `authorizer.Authorized(r)` 做鉴权，未配置 token 时任何请求都通过。
**原因**：`auth/bearer.go:17-20` —— `if !b.Enabled() { return true }`，`Enabled()` 即 `Token != ""`（`:13-15`）。
**规避**：所有调用点必须前置 `cfg.AuthToken != ""`。范本见 `httpx/mcp_endpoint.go:45`：`staticOK := cfg.AuthToken != "" && authorizer.Authorized(r)`。

### A2 未认证 + 回环绑定时 `/internal/runtime/*` 对本机任意进程开放

**现象**：开发者以为"只监听 127.0.0.1 就安全"，但本机任何进程（含恶意浏览器扩展、其它应用）都能读写任务与插件。
**原因**：只有 `/internal/runtime/analytics` 有回环闸门（`runtime_api.go:49-53`）；其余路径在未启用认证时直接放行。
**规避**：生产环境必须设 `AGENTDOCK_AUTH_TOKEN`（compose 里是必填项）；本地开发接受该风险时也要知道边界。

### A3 静态 Token 无限流

**现象**：`/mcp` 与 `/context` 的 Bearer 失败没有退避，可在线穷举。
**原因**：限流器只挂在 OAuth 路由（`/register` 30/min、`/oauth/authorize` POST 10/5min，`oauth.go:58-73`），静态 Bearer 校验路径无限流。
**规避**：token 必须高熵；公网部署加前置代理限流。

### A4 客户端 OAuth 凭证明文落盘

**现象**：拿到设备文件系统即可读走 refresh token。
**原因**：服务端 OAuth 状态只存 SHA-256，但**客户端侧** `data/mcp/clients.json` 与 `grant-*.json` 明文存 `client_secret` / access / refresh token（`mcp/oauthclient/store.go:26-51`、`:107-130`、`:174-196`）。权限是 0600/0700（`:69`、`:126`、`:193`），仅靠文件权限保护。
**规避**：把 `data/mcp/` 视同凭据目录；不要在日志/诊断里 dump 这些文件。

### A5 `filepath.Clean` 不是安全边界

**现象**：以为 `Clean` 后不含 `..` 就安全，实际可被符号链接绕过。
**原因**：`workspace.Clean`（`workspace.go:191`）注释明示不是安全边界；`ResolveForWrite` 在 `EvalSymlinks` 与写入之间存在 TOCTOU 窗口。
**规避**：用 `os.OpenRoot` / `OpenInRoot` + `filepath.IsLocal` + `filepath.Rel` 三重校验。

### A6 stdio 路径无 panic recover

**现象**：一个工具的 handler panic 导致整个进程退出。
**原因**：`serveStdio`（`cmd/agentdock/server.go:164-173`）与 `mcp.Server.ServeStdio` 都没有 `defer recover()`。HTTP 路径由 `net/http` 兜底，stdio 没有。
**规避**：handler 内不 panic；插件/第三方工具入口必须自行 recover。

## B. 并发与死锁（4 条）

### B1 `Runtime.Close` 中持有 `lifecycleMu` 会死锁

**现象**：关闭时卡住。
**原因**：`runtime.go:212-214` 明确注释 —— `command.BeginClose()` 与 `WaitForStarts()` **不得**持 `lifecycleMu`。
**规避**：`Close` 的第一段只做"设 `closing` 标志 → 解锁"，后续动作在锁外。改 `Close` 顺序前先读那段注释。

### B2 Plugin 三级租约用错层级

**现象**：长任务执行中插件版本目录被 GC 删掉。
**原因**：`plugin/store.go:457 AcquireBinding` 只保护 `state → version` 的解析窗口；长期工作必须升级到 `AcquireVersionRead`（`:615`）。注释原文说明了这一点。
**规避**：拿到具体版本路径后立刻 `AcquireVersionRead`，用完释放；不要用 Binding 的租约跨越实际工作。

### B3 Plugin reconcile 卡死时恢复逻辑只等 150ms

**现象**：进程崩溃后重启，插件状态长时间不恢复。
**原因**：`manager.go:1011-1025` 的 `recoverInterruptedActivations` 每次 `AcquireWrite` 只给 150ms；拿不到就认为"另一个活进程仍持有"，跳过。若那个进程已死但锁未 stale（`staleAfter=25h`），就要等到 stale。
**规避**：正常路径不要长时间持有 plugin 写锁；异常后若确认无活进程，可手工删锁文件。

### B4 更新回滚必须脱离父 ctx

**现象**：用户取消更新，回滚被一起取消，留下半提交状态。
**原因**：回滚需要独立时间预算，`updateengine/arbiter.go:105-119` 用 `context.WithoutCancel` + 3 分钟超时。
**规避**：任何"清理/回滚"路径都不能直接用请求 ctx。

## C. 路径与文件（2 条）

### C1 同一版本不同摘要 → 永久冲突

**现象**：插件更新报 `PLUGIN_VERSION_DIGEST_CONFLICT`，之后无论怎么重装都失败。
**原因**：非 local 版本的同版本异摘要被视为不可调和，**没有强制覆盖入口**。
**规避**：发布侧保证"同版本号 = 同内容"；一旦发生只能升版本号。

### C2 Windows 测试不得留未跟踪文件

**现象**：本地全绿，Windows CI 在"洁净检查"步骤失败。
**原因**：`ci.yml` 的 Windows job 跑 `git ls-files --others --exclude-standard`。
**规避**：测试的临时文件写 `t.TempDir()`；不要写到仓库根。

## D. 更新与发布（4 条）

### D1 `v1.0.0` 未设 `LEGACY_GITHUB_LATEST_TAG` 会直接失败

**现象**：发布 job `exit 1`。
**原因**：`release.yml:1547-1549`。v0.9.x 客户端把 GitHub `releases/latest` 当更新 API，必须保留兼容桥，否则老客户端会跳到 v1.0.0 跳过迁移。
**规避**：在 repo variables 里设一个**已发布的、非 draft、非 prerelease** 的旧 tag；且不能等于本次 tag。

### D2 Windows ≤v0.7.4 只替换 core

**现象**：从很老的版本升级后桌面端行为异常。
**原因**：旧版本更新只换 core 二进制，靠 `selfupdate.RepairDesktopRuntimeIfNeeded` 启动时补齐；补齐失败**只告警**，不阻断启动。
**规避**：补齐失败会在下次启动重试；排查时看启动日志里的 `startupdiag`。

### D3 staged `install.ps1` 与源码比对不能用 `Get-FileHash`

**现象**：发布校验误报不一致。
**原因**：Windows checkout 可能改写行尾；必须用 `git hash-object --no-filters` 对齐 Git blob（`ci_workflow_test.go:190-200`）。
**规避**：不要在发布脚本里引入 `Get-FileHash` 做这层比对。

### D4 macOS 自签名连续性只认同一 thumbprint

**现象**：自签名构建升级后需要用户重新授权。
**原因**：签名连续性检查只在同 thumbprint 下通过；`updateplatform/darwin.go:307-357` 的签名连续性逻辑。
**规避**：本地发布保持一致签名身份；否则预期用户重新授权。

## E. Plugin 与 MCP（5 条）

### E1 `review_token` 不是授权

**现象**：以为拿到 token 就能安装。
**原因**：token 只是内容标识（`review-v1:sha256:<digest>`）；真正安装仍要重新 stage 并校验同一快照。
**规避**：把 `inspect`/`validate`/`install` 视为三步原子流程的语义，而不是"审核通过就免检"。

### E2 `state.json` 不含 MCP 明文

**现象**：插件在 state 里显示"已安装"，但 MCP server 起不来。
**原因**：`stateComponentIndex` 剥离了 MCP 明文；真实配置在 `mcp.json` 或 envstore，包目录不可读时引用失效。
**规避**：排查"MCP 不启动"先看 `mcp.json` 与 envstore，不要只看 `state.json`。

### E3 `mcp.json` 静默降级面很大

**现象**：用户配了 server 但没生效，日志没明显错误。
**原因**：非法 JSON / 缺 `mcpServers` / 未知字段都**只 warning 不激活**。
**规避**：改 `mcp.json` 后查 `internal/runtime/mcp` 列表与 `last_error`。

### E4 `internal/mcp/registry.go` 与 `schema.go` 不是你以为的东西

**现象**：按名字找注册表/校验器，读到空的或一行的文件。
**原因**：`registry.go` 只有一行类型别名，`schema.go` 是空文件。
**规避**：真实入口是 `mcp/client.Manager` 与 `tool/contract`。

### E5 purge tombstone 后不可回滚

**现象**：插件 `remove` 用 `data_policy: purge` 后想恢复数据。
**原因**：purge 后数据已删，事务只能前向重试，不能回滚。
**规避**：`remove` 默认用 `keep`；purge 前必须确认。

## F. 状态机与语义（3 条）

### F1 "统一 Schema 校验"必须限定范围

**现象**：文档说"统一 Zod/Schema 校验"，读者以为输出也校验。
**原因**：只有 input validator 被编译（`specs_validation.go:16`），output schema 不参与运行时校验。
**规避**：表述为"输入侧 + 启动期 fail-fast"。

### F2 Nexus 单次 tool panic 会变成 `NODE_OPERATION_FAILED`

**现象**：云端看到一条工具调用失败，但设备进程还活着。
**原因**：`nexusbridge/client.go:288-303` 的 `recover()` 刻意收敛 panic，不扩散到进程。
**规避**：这是设计而非 bug；排查要查 panic 日志而非进程崩溃。

### F3 Nexus 旧 env 凭据启动即失效

**现象**：设了 `AGENTDOCK_NEXUS_ENDPOINT` / `AGENTDOCK_NEXUS_TOKEN` 不生效。
**原因**：`cmd/agentdock/server.go:33-35` 启动时 `os.Unsetenv` 两者；凭据只能来自 `~/.agentdock/nexus/device.json`。
**规避**：用 `agentdock nexus pair` 配对；环境变量只作为**配对完成前的临时输入**，运行期不再读。

## G. ACP（1 条）

### G1 steering 竞态

**现象**：偶发"旧 run 未取消就发生 steer"。
**原因**：`prompts.go` / `prompt_settle.go` / `compatibility.go` 的时序依赖（回归用例在 `steering_compatibility_test.go`）。
**规避**：改上述实现文件必须跑 `-count=20` 的 race 回归——**完整命令只在** → 详见 [测试策略 § 竞态测试](../05-项目开发规范/测试策略.md#3-竞态测试)。
